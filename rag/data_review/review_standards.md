# 代码审查规范指南

> 本文档是代码审查助手在进行代码评审时引用的规范基线。每条规范编号为 Rx.y,审查时可直接引用编号定位依据,如"违反 R3.1:外层缩进应为 4 空格"。

## 1. 评审总则

R1.1 评审以"问题能复现、改进可落地"为原则。指出缺陷时给出场景和原因,不要只说"这里不好"。

R1.2 区分严重级别:
- 严重(阻塞合并):安全漏洞、数据丢失、逻辑错误、性能灾难、引入无法回退的破坏性变更。
- 一般(建议修复):可读性差、违背约定、重复代码、缺少边界处理。
- 提示(可选):风格微调、命名建议、注释建议。

R1.3 评审意见聚焦代码本身,不针对开发者。所有建议都应是可执行的修改指令。

R1.4 每个高风险变更(涉及安全、支付、权限、数据迁移)至少要有两人确认:作者自审 + 一名独立评审者。

R1.5 合并前必须满足:单元测试通过、评审意见的"严重"级全部解决、"一般"级给出处置决定(修或明确不修及理由)。

R1.6 评审范围应聚焦本次改动,不要为了彰显专业而review整个文件无关区域。范围外的发现单独记录,不入本次阻塞项。

R1.7 若改动引入了新的依赖,必须说明依赖的必要性、体积影响、许可证(license)是否允许商用。

## 2. PEP 8 风格规范(Python)

R2.1 缩进统一为 4 空格,禁止使用 Tab 缩进混排。PEP 8 明确规定每级缩进用 4 空格。

R2.2 每行代码不得超过 79 个字符(PEP 8 建议),团队可放宽到 99/120,但必须一致。超长行要拆行,续行用括号包住或反斜杠显式续行。

R2.3 顶层函数和类之间空两行;类内方法之间空一行。空白用于表达层级,不是装饰。

R2.4 import 顺序:PEP 8 要求标准库、第三方、本地模块三组,每组内按字母序,组间空一行。参考分组 import 重排。

R2.5 命名规范:
- 模块/包名:全小写,单词用下划线分隔(如 `parse_html`)。
- 类名:CamelCase(如 `ParseHTMLHandler`)。
- 函数/变量/方法:snake_case(如 `parse_html`、`max_retries`)。
- 私有成员:前缀单下划线 `_internal`;避免双下划线(名称改写)`__dunder` 除非有意触发名称改写。
- 常量:全大写加下划线(如 `MAX_RETRY_TIMES`)。

R2.6 不要用 `== None` 或 `!= None`,应使用 `is None` / `is not None`。因为 None 是单例,身份比较才精确。

R2.7 布尔值不要写成 `if x == True` 或 `if x == False`,直接 `if x:` / `if not x:`。

R2.8 比较空容器用隐式真值:`if not items:` 而非 `if len(items) == 0:`。

R2.9 字符串拼接:少量固定片段可用 `+`;动态多段优先用 f-string(Python 3.6+)或 `join`,避免在循环里 `+=` 反复构造字符串(会导致 O(n^2))。

R2.10 导入只用实际使用的符号,避免 `from module import *`,它会污染命名空间、破坏显式性。

## 3. 命名与可读性

R3.1 命名必须表达"是什么/做什么",禁止使用 `a`、`x1`、`tmp` 这类无法自解释的短名(循环变量 `i`/`j` 除外)。

R3.2 布尔变量名用 is/has/should 开头,读起来像问题(如 `is_valid`、`has_permission`),避免 `flag`、`status_1`。

R3.3 动词开头命名函数/方法(`get_user`、`save_file`);名词命名类;名词或形容词结构命名变量。

R3.4 布尔参数(`enable_xxx`)除非调用处也已明确,否则考虑用两个明确命名的函数或用关键字参数,避免死魔法布尔。

R3.5 注释说明"为什么"而非"是什么"。代码本身应能自解释要做什么;注释专讲设计意图、权衡、陷阱。

R3.6 不保留被注释掉的死代码。既有的历史改动用版本控制管理,注释掉的代码只会误导后来者。

R3.7 函数/类应有 docstring,说明用途、入参、返回值;公开 API 尽量给复杂参数和行为示例。

R3.8 一个函数只做一件事(Single Responsibility 的函数粒度)。如果一个函数能拆成两句"这个函数负责 X"说不清,就该拆。

## 4. 复杂度与可读性规范

R4.1 圈复杂度(Cyclomatic Complexity)建议 <= 10。超过时拆分子函数,不要无限叠加 if/elif/for/while。

R4.2 反对深层嵌套:嵌套深度最多 3 层。超过就正面用"提前返回(early return)"或拆分函数拉平。

R4.3 函数长度:单个函数体(不含 docstring)建议 <= 50 行。超过意味着职责过多或做了多层抽象,应拆分。

R4.4 使用"提前返回"避免层层 if-else 的快乐路径被淹没。先处理异常/边界,再放主体逻辑。

R4.5 魔法数字要命名:裸的 `60`、`86400`、`0.85` 一律提出去用常量,并给常量有意义的名字。

R4.6 避免布尔参数切换函数的两种完全不同行为。如果 `do_thing(False)` 和 `do_thing(True)` 行为差异巨大,拆成两个函数。

R4.7 复杂条件表达式拆成描述性的中间布尔变量,如 `is_upgradable = version >= MIN and not forbidden`。

R4.8 使用 Python 内置特性降低复杂度:`any`/`all`/`dict.get(..., default)`/`enumerate`/`zip`/`collections.Counter`,不要手写低效循环。

## 5. 常见反模式(代码坏味道)

R5.1 重复代码(DRY):同一逻辑出现三处以上,应提取为公共函数/工具。复制粘贴是返工和 bug 的来源。

R5.2 隐藏的全局状态:不要用模块级可变全局变量做业务状态。状态该放显式对象/上下文,便于测试和并发。

R5.3 God 类/Object:一个对象承担过多职责、方法多而杂,应拆分为高内聚类。

R5.4 过度工程:在无明确需求时为不可预见的"未来"添加抽象层、配置化、扩展点。YAGNI——只实现当下需要。

R5.5 快照式对吗:string 或 dict 作为万能数据结构传遍全层,导致类型不明确、字段名写错编译器不报错。用 dataclass/typing。

R5.6 早退反模式:在 `finally` 里改变返回值或重抛,会掩盖原始错误。

R5.7 空接口/空类:定义了但不使用的抽象/接口,先删。

R5.8 长参数列表:函数参数超过 6 个,考虑把相关参数打包进一个参数对象(dataclass)或 options dict。

## 6. 安全编码规范

R6.1 五条安全底线(严重级):
- SQL/查询注入:任何用户输入进入数据库查询前必须参数化(占位符),禁止字符串拼接 SQL。
- XSS:任何用户内容渲染到 HTML 前必须转义/编码,禁止把 `innerHTML` 直接赋用户输入。
- 授权边界:服务端必须校验每个请求的权限,不能只靠前端隐藏按钮。
- 敏感信息:日志/报错/响应里不得泄露密码、token、密钥、身份证号、手机号。
- 输入校验:所有外部输入(长度、类型、范围、白名单)必须先校验再做后续操作。

R6.2 密码存储:必须用慢哈希(如 bcrypt/argon2)加盐存储,禁止明文、禁止裸 MD5/SHA1。

R6.3 密钥管理:不在代码里硬编码密钥/token,用环境变量或密钥管理服务。密钥泄露要立即轮换。

R6.4 认证 token:过期时间要短,支持撤销,传输全程用 HTTPS。不要把 token 放 URL 或日志。

R6.5 越权防护(BCA):防止水平越权和垂直越权。每个读改写操作都要验证"该用户是否有权访问该资源"。

R6.6 路径穿越:处理文件路径时,规范化并校验其落在允许的目录内,防止 `../../etc/passwd`。

R6.7 反序列化:不要反序列化不可信输入到泛型对象(如 `pickle`)，可能导致 RCE。用安全格式如 JSON 并校验 schema。

R6.8 依赖安全:新依赖先查已知 CVE;使用锁文件锁定版本,避免意外的破坏性升级。

R6.9 SSRF:服务端去请求外部 URL 前,校验目标域名/IP 不在内网段(如 169.254.169.254 元数据地址),防止探测内网。

R6.10 内容安全:重定向目标必须校验为白名单;下载文件名要白名单;设置合理的 CSP 头。

## 7. 错误处理与边界条件

R7.1 错误捕获要具体:用特定异常类型(`ValueError`、`KeyError`),不要裸 `except:` 吞掉一切(它会吞掉 KeyboardInterrupt/SystemExit 和 bug)。

R7.2 捕获异常后要处理,不能空 `pass` 静默。确实需要吞掉时要注释说明为什么安全。

R7.3 自己抛异常时,给清晰的中文/可读信息,包含出错的上下文(哪个输入导致)。不要抛出空 `raise Exception("fail")`。

R7.4 边界条件必查:空输入、None、0/负数、超长输入、单元素、大数溢出、时区/闰秒。

R7.5 防御输入而非假定:外部 API 返回的字段可能缺失/类型不对,用 `.get()`/类型检查兜底,严禁无保护下标访问。

R7.6 资源清理用上下文管理器:`with open(...)`/`with lock:`。手动 open 后必须保证异常路径也 close。

R7.7 避免过早吞异常导致"某个错误被当成另一个情况的正常返回"。错误应在上层可感知的地方收敛处理。

## 8. 性能规范

R8.1 明确复杂度上限。O(n^2) 及以上的核心路径需在注释或用例中说明数据规模假设,否则直接用线性或预计算/缓存方案。

R8.2 循环内重复查询数据库/调外部 API 是高危反模式(N+1)。批量拉取再内存处理。

R8.3 内存复用:避免在循环里拼接超大字符串、反复复制大列表;生成器 `yield` 处理流式大数据。

R8.4 缓存要有失效策略,不能无限缓存。缓存 key 要涵盖所有影响结果的入参。

R8.5 数据库:为高频查询字段建索引;避免 SELECT * 全表拉取;批量写用事务归一。

R8.6 并发安全:共享可变状态须加锁或用不可变/线程安全容器;避免死锁(锁顺序固定一致)。

R8.7 懒加载要权衡:首次调用慢时用 `lru_cache`/单例预先加载,但要注明初始化代价。

## 9. 测试规范

R9.1 每个新功能/修复必须带单元测试。修复 bug 的测试要先复现原 bug(先红)再修复(变绿)。

R9.2 测试命名用"should/测试目标_条件_期望"风格,如 `test_pay_insufficient_balance_raises`。

R9.3 测试要独立:不依赖执行顺序、共享全局状态、真实时间/网络/数据库。用依赖注入或 mock。

R9.4 断言要具体:断言期望值,不要只断言"不抛异常"。覆盖边界和错误分支。

R9.5 关键异常分支、权限分支、以及所有 R6 安全路径必须有测试覆盖。

## 10. 并发与资源管理

R10.1 使用 `asyncio`/线程池时,注意共享资源的互斥;协程里不要长时间阻塞事件循环。

R10.2 任务/线程要有明确的回收路径,防止泄漏(`.cancel()`/`.join()`/`with Executor`)。

R10.3 设置合理的超时:所有网络/外部调用必须有 timeout,禁止无限等待导致挂死。

R10.4 幂等性:涉及重试的操作要对重复提交友好(有幂等 key 或天然幂等),防止网络抖动造成脏数据。

R10.5 配置与环境的分离:硬编码环境差异(地址、开关)提到配置,便于测试不同环境。

## 附:评审快捷参考

- 快查"这条代码有什么问题"→ 对照第 4 章(复杂度)、第 5 章(反模式)。
- 快查"安全漏洞"→ 第 6 章,逐条过 R6.1~R6.10。
- 快查"会不会数据出错/崩溃"→ 第 7 章。
- 快查"慢不慢"→ 第 8 章。
